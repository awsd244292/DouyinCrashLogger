# 取证能力边界（能测到什么 / 测不到什么）

> 这份文档存在的唯一目的：**防止误判**。
> 日志里"没有记录"有两种截然不同的含义 —— 「确实没发生」和「我们够不着」。
> 把它们混为一谈，就会把「蹲错楼层」当成「探针写漏了」，然后往一条根本不会被
> 调用的路径上反复加钩子，白干很久还得不出结论。

标注：本文全部为经验判断，无官方来源。涉及 iOS 系统框架的 API 名称可查
[Apple Developer Documentation](https://developer.apple.com/documentation)，
但「抖音是否走这些 API」无法证实。

---

## 一、硬前提

非越狱注入的 dylib 与抖音宿主同处一个进程，但：

1. **改变不了宿主进程内存**，只能观测与旁路打点；
2. **进不了抖音自研的私有实现**，拿不到其内部状态机；
3. 抖音是闭源二进制，**无符号表**，崩溃栈里属于它的帧基本是 `0x0000000102xxxxxx` 裸地址。

所以本插件追求的从来不是"深入抖音内部"，而是——**在够得着的那一层，把证据采集到最大**。

---

## 二、能测到的（按可靠度排序）

| 层级 | 取证点 | 可靠度 | 说明 |
|---|---|---|---|
| 系统层 | 音频会话中断 / 路由变更 | 高 | 通知必达，不依赖播放器实现 |
| 系统层 | 前后台 / 锁屏 / 内存警告 | 高 | 同上，App 生命周期通知 |
| 宿主外显 | 触摸事件时刻 | 高 | `sendEvent:` 钩子，只能证明"有触摸"，不能证明"点了暂停" |
| 系统层 | 主线程卡顿时长与栈 | 中高 | `CFRunLoopObserver`（公开 API）+ 栈采样 |
| 系统层 | 崩溃信号 / OC 未捕获异常 | 高 | 信号 handler + `NSSetUncaughtExceptionHandler` |
| 公开框架 | AVPlayer 的 pause/play/setRate: | **不确定** | 仅当抖音走系统播放器时有效，见下节 |
| 时间线 | 上述所有事件的因果对齐 | 高 | 共用 `mach_absolute_time`，可回答"暂停前 200ms 发生了什么" |

---

## 三、测不到的清单（诚实版）

**以下各项，任何非越狱方案都拿不到。日志里若没有它们，属于预期，不是 Bug。**

1. **抖音自研播放器内部为何调用 pause** —— 拿不到私有实现，也拿不到其内部状态机。
2. **是否播放器内部状态机主动暂停** —— 同上。
3. **抖音自研网络栈（如 TTNet）的内部请求与加载细节** —— 只在其走 `NSURLSession` 时可见。
4. **抖音私有渲染 / 特效管线内部** —— 拿不到。
5. **SIGKILL 的真实死亡原因**（OOM 还是 watchdog）—— 信号 9 应用层拦不住，
   只能靠"非正常退出标记"与系统 Jetsam 日志推断。
6. **主线程 watchdog 杀** —— 只能提前预警卡顿，拦不住被杀。
7. **崩溃栈里抖音私有帧的符号** —— 无 dSYM，永远是裸地址。

## 四、决策树：日志没抓到暂停，该怎么判断

遇到"视频确实停了但日志没记录"，按顺序自查，**不要一上来就加钩子**：

```
时间线里有没有「AVPlayer实例」这一行？
│
├─ 有（创建过 AVPlayer 实例）
│   → 系统播放器路径是通的、钩子也挂上了
│   → 结论：这次暂停没走 AVPlayer 的 pause/play 调用
│   → 下一步：看时间线里同期有没有「主线程卡顿」——
│              有，则画面是被冻住而非主动暂停；
│              没有，则大概率走了另外一路播放器。
│
└─ 没有（全程未见 AVPlayer 实例）
    → 强烈提示抖音主播放不走系统 AVPlayer（自研引擎）
    → 结论：AVPlayer 钩子命中不了是**预期结果**，不是探针写漏
    → 下一步：不要再往 AVPlayer 上加钩子（加多少都是零），
              改用系统层信号（音频中断/前后台/锁屏）+ 时间线做侧证。
```

补充判据：运行时枚举 `AVPlayer` 的子类（只读 `objc_getClassList`，零 hook，
safe 档也执行）。枚举到子类说明抖音基于系统播放器做过扩展；一个都没有则更倾向自研引擎。

## 五、探针纪律（避免自己制造问题）

这套取证最大的讽刺在于：**探针太重，它自己就是卡顿来源**。
因此立下四条规矩，改代码时请遵守：

1. **默认最小**：采集方案默认 `safe`（零 hook），需要深挖才手动开 `full`。
2. **环形缓冲有界**：时间线固定 512 条，满则覆盖最旧；绝不无界增长。
3. **钩子体只打点**：不分配堆内存、不拿锁、不做 IO、不符号化；
   符号化等重活一律丢后台串行队列。
4. **快照只留触发窗口**：不做全量 dump，只保留触发前后那一段。

违反任一条，取证手段本身就会变成新的卡顿源 —— 那等于用测速仪制造堵车。

---

## 六、结论能推到哪一层

| 用户的问题 | 能给出的答案 | 到不了的层 |
|---|---|---|
| 视频什么时候停的？ | 系统层精确到毫秒；自研播放器只能给旁证时刻 | 抖音内部 pause 的调用点 |
| 是不是我点的？ | 时间线里"触摸 → 暂停"相邻可高度提示 | 无法确认那个触摸落在暂停键上 |
| 是不是系统打断的？ | 能确证（音频中断 / 路由变更 / 前后台 / 锁屏有明确时间戳） | — |
| 是不是卡住了？ | 能确证（主线程卡顿时长 + 栈 + 归因） | 抖音私有线程内部 |
| 抖音**为什么**主动暂停？ | 拿不到，这是硬限制 | 自研播放器内部状态机 |

一句话总结：**能建立到"系统层 + 宿主外显层"的因果，到不了"抖音内部为什么"这一层。**
